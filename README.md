# Data Agent

text-to-SQL 데이터 분석 에이전트. 661만 건 이커머스 행동 로그 기반으로 만듦(최대한 정제되지 않은 데이터 기반으로 실행하기 위함).

간단한 질문에 좋은 답이 나오는 것, 모르는 건 모른다고 하는 것. 이 두 가지를 목표로 잡았다.

---

## 왜 만들었나

분석할 때 시간을 제일 많이 쓰는 건 최종 쿼리가 아닌 그 앞단.

이 컬럼 결측이 몇 퍼센트지. 이 값이 몇 종류나 있지. 조인 키가 유일한가. 매번 비슷한 쿼리를 새로 치는데, 이걸 데이터 에이전트로 대체하면 어떨까 해서 시작함.

그런데 만들다 보니 더 큰 문제가 있었다. LLM한테 "전환율 얼마야"라고 물으면 **매번 다르게 계산한다.** 세션 기준으로 했다가, 유저 기준으로 했다가, 이벤트 기준으로 했다가. 셋 다 틀린 건 아닌데 숫자가 다르다. 

그래서 방향을 바꿨다. **쿼리를 잘 짜는 것보다 정의를 고정하는 게 먼저다.**

---

## 이 데이터에서 먼저 확인한 것

구현 전에 데이터부터 뜯어봤다.

**구매의 절반이 장바구니를 거치지 않는다.**

```
전체 구매      106,966건
├─ 장바구니 거침  53,387건 (50%)
└─ 바로 구매     53,579건 (50%)
```

이게 왜 중요하냐면, 퍼널을 전제한 순간 답이 달라진다.

| | 계산 | 결과 |
|---|---|---|
| 퍼널 전제 | 구매 106,966 ÷ 장바구니 124,252 | **86%** |
| 실제 | 고유 (유저, 상품) 조합 기준 | **48%** |

86%가 나오면 "장바구니까지 온 사람은 대부분 산다, 문제는 조회→장바구니 구간"이라고 읽게 된다. 근데 분자의 절반은 장바구니에 담은 적도 없는 구매다. 진단 방향이 반대로 간다.

이 발견 때문에 **"장바구니 이탈률"이라는 지표를 아예 정의하지 않았다.** 구매의 절반에 적용되지 않는 개념을 지표로 만들어두면 언젠가는 쓰게 되기 때문이다.

에이전트한테 똑똑한 답을 요구하는 대신, 틀릴 수 있는 정의를 미리 제거해두는 쪽을 택했다.

---

## 이런 식으로 동작한다

**규칙 없이 물으면**

> 장바구니에서 구매까지 전환율이 어떻게 돼?

```
86.1%
```

SQL도 돌아간다. 근데 틀렸다.

**정의 파일을 참조하면**

> 장바구니에서 구매까지 전환율이 어떻게 돼?

```
48.26%

고유 (user_id, product_id) 조합 기준으로 계산했다.
cart 이벤트 총합을 분모로 쓰면 같은 상품 재담기가 중복 계산되어
값이 부풀려진다.

참고: 이 데이터는 구매의 약 50%가 cart를 거치지 않는다.
순차 퍼널로 해석하면 안 된다.

실행 SQL:
WITH cart_items AS (...)
```

## 구조

```
Claude Code                 ← 질문을 받고 계획을 세운다
     ↕ MCP
src/server.py               ← 도구 4개
     ↕
weblog.db (SQLite)          ← 661만 행

CLAUDE.md                   ← 항상 지켜야 할 규칙
metrics.yaml                ← 지표 정의
```

별도 오케스트레이션 계층은 만들지 않았음. 규칙 파일과 도구 설계만으로 다단계 분석이 나오는지 보고 싶었기 때문.  (아래 평가 부분에 예시가 있다)

---

## 도구

| 도구 | 하는 일 |
|---|---|
| `list_tables()` | 테이블 목록 |
| `get_schema(table, where=None)` | 컬럼·타입·**결측률**·카디널리티 |
| `run_query(sql)` | 읽기 전용 SELECT |
| `get_metric(name, period, segment)` | 정의 파일 기반 지표 계산 |

**`get_schema`가 결측률을 같이 준다.** 분석 초반에 제일 자주 치는 쿼리라서 아예 스키마 조회에 붙였다. `lru_cache`로 반복 호출은 캐시된다.

**`where=`를 넣은 이유가 있다.** 전체 결측률과 조건부 결측률이 다르기 때문이다.

```python
get_schema("events")
# category_code 결측률 32.57%

get_schema("events", where="event_type='purchase'")
# category_code 결측률 24.42%
```

이게 없으면 에이전트가 전체값을 그대로 인용한다. 구매 데이터만 분석하면서 32.57%라고 말하는 상황이 생긴다.

**`run_query`에는 세 가지를 걸었다.**
- SELECT만 허용
- 결과 1000행 상한
- 실행 전 `EXPLAIN QUERY PLAN`을 돌려서 전체 스캔이면 경고를 붙임

경고는 막는 게 아니라 알려주는 용도다. 661만 행이면 전체 스캔이 불가피한 질문도 많다.

## 안 하는 것

지어내지 않는 게 제일 중요하다고 봤다. 분석가는 결과를 그대로 보고에 쓴다.

| 상황 | 동작 |
|---|---|
| 데이터 기간(2019년 10월) 밖 질문 | 계산 안 하고 왜 불가능한지 말한다 |
| 결측률 10% 넘는 컬럼 집계 | 실제 결측률을 응답에 명시 |
| 정의에 없는 지표 | 임의로 계산하지 않고 되묻는다 |
| "왜 떨어졌어?" | 어디서 떨어졌는지까지만. 원인은 데이터 밖 정보가 필요하다고 밝힌다 |

결측 임계치를 10%로 잡은 건 brand 때문이다. 20%로 잡으면 brand(16.2%)가 그냥 통과한다.

## 평가

**구현보다 평가 문항을 먼저 만들었다.** 나중에 만들면 이미 만든 기능에 유리한 문항만 고르게 된다. 20문항과 정답 SQL, 정답 숫자를 먼저 고정하고 시작했다.

```
단순 집계        5
필터·그룹핑      5
지표 계산        5
다단계 분석      3
답할 수 없는 질문  2
```

마지막 두 개가 중요하다. **답할 수 없는 질문에 답하지 않는 것도 능력이다.**

채점은 세 갈래로 한다.

```
eval/score.py
├─ 값 대조     스칼라·표를 정답과 비교
├─ 거부 판정   불가 사유를 말했는지, 추측값을 안 냈는지
└─ 루브릭     분석 문항은 항목별 수동 확인
```

### 결과

자동 채점 18문항 중 16문항 통과.

| 유형 | |
|---|---|
| 단순집계 | 8/8 |
| 지표 | 5/5 |
| 세그먼트 | 2/3 |
| 답할 수 없는 질문 | 1/2 |

### 틀린 2개가 같은 이유로 틀렸다

이게 이 프로젝트에서 제일 건진 부분이다.

**q15 — 주중/주말 전환율**

세션의 요일을 뭘로 볼지 정해두지 않았다. 세션이 자정을 넘길 수 있으니까 첫 이벤트 기준인지 마지막인지 정해야 하는데, 그 규칙이 **정답셋 파일에만 있고 에이전트가 읽는 파일에는 없었다.** 알려주지도 않고 맞히길 기대한 셈이다.

`metrics.yaml`에 규칙을 넣고 다시 물었더니 정답과 소수점까지 일치했다.

**q20 — 미분류 상품의 카테고리별 매출**

답할 수 없는 질문이고, 에이전트는 정확히 "계산 불가"라고 했다. 근데 참고로 다른 숫자를 하나 덧붙였다. 질문한 것과 다른 값이라 답으로 오인될 수 있다.

이것도 규칙이 없었다. "거부할 땐 참고 수치도 내지 마라"를 어디에도 안 적어뒀다.

**결론: 에이전트가 못한 게 아니라 규칙이 닿지 않았다.** 규칙이 에이전트가 읽는 파일에 있어야 효과가 있다. 평가 인프라에만 있으면 없는 거나 마찬가지다.

### 점수를 손보지 않은 이유

q15는 값이 맞았으니까 응답 파일만 고치면 17/18이 된다. 목표치였다.

안 고쳤다. 출력 형식이 틀린 건 에이전트가 실제로 그렇게 낸 거고, 내가 고쳐 넣으면 형식을 지키는지를 못 재게 된다.

대신 내가 응답을 옮겨 적다가 컬럼을 빠뜨린 3건은 복원했다. **에이전트가 낸 결과와 내 실수는 구분해야 한다.**

### 분석 문항은 이렇게 답했다

루브릭 문항 하나를 그대로 옮긴다.

> Q. 오후 시간대(14~17시)는 조회 수가 가장 많은데 전환율은 가장 낮다. 데이터에서 확인 가능한 요인은?

에이전트가 한 것:

1. **전제부터 확인했다.** 질문은 14~17시라고 단정했는데, 24시간을 다 계산해보니 15~17시에만 성립했다. 틀린 전제를 그대로 받지 않았다.
2. **비율 착시인지 봤다.** 14~17시는 세션이 오전보다 45% 많은데 구매 세션 수는 오히려 적었다. 분모만 커진 게 아니라 실제로 줄어든 거였다.
3. **가설 3개를 세우고 전부 기각했다.** 봇 비중, 상품 구성, 세션당 조회 수. 특히 세션당 조회 수는 "18시 이후엔 전환율이 다시 오르는데 조회 수는 계속 증가한다"는 반증으로 걷어냈다.
4. **원인은 말하지 않았다.** 트래픽 소스나 기기 정보가 이 테이블에 없어서 확인할 수 없다고 밝혔다.

별도 계획 수립 코드 없이 규칙 파일만으로 나온 동작이다.

한 가지 더 알게 된 건, **같은 질문을 다시 물으면 결론이 달라질 수 있다는 것.** 1차에서는 세션당 조회 수를 연관 요인으로 채택했는데 재실행에서는 기각했다. 재실행 쪽이 더 타당했지만, 분석 문항은 한 번 돌린 결과를 성능 수치로 쓰면 안 된다는 뜻이기도 하다.

## 해보고 버린 것

**`price_band` 세그먼트 축.** 가격대별로 전환율을 비교하려고 했는데, 사분위로 경계를 나누니 구매 건수가 강제로 균등해져서 세그먼트 간 차이가 안 보였다. 빼고 브랜드 결측 여부·시간대·카테고리로 바꿨다.

**커버링 인덱스.** 쿼리 하나가 18분 걸려서 인덱스를 만들려고 했는데, 다시 돌려보니 재현이 안 됐다. 원인은 그 앞에 잘못 짠 쿼리를 15분간 붙들고 있었던 것.

**정의 파일의 잘못된 주의사항.** `cart_to_purchase_rate`에 "실제 값 37%"라고 적어뒀는데 돌려보니 48.26%였다. 검증 없이 적어둔 수치라 정정했다. 주의사항이 틀리면 그걸 참조한 답이 전부 달라진다.

## 지금 한계

- **출력 규격이 질문 프롬프트에 있다.** `CLAUDE.md`로 옮겨야 하는데, 옮기면 20문항을 다 다시 돌려야 해서 미뤘다. 일부만 돌리면 실행 조건이 섞여서 점수가 의미를 잃는다.
- **`run_query`에 타임아웃이 없다.** 오래 걸리는 쿼리를 손으로 끊어야 한다. `set_progress_handler`로 상한을 걸 계획.
- **채점기가 `"8.895%"`와 `0.08895`를 다른 값으로 본다.** 콤마·퍼센트 기호를 정규화해야 한다.
- **자동 러너를 못 돌렸다.** `eval/run_agent.py`는 만들어뒀는데 API 크레딧이 없어서 20문항을 수동으로 실행했다. 문항별로 새 세션을 열어 격리는 했지만 도구 호출 기록을 손으로 옮겼고, 거기서 전사 오류가 났다.
- **단일 월 데이터다.** 전월 대비나 월 단위 코호트는 애초에 불가능하다.

## 다음

이 데이터셋에 맞춰 만든 걸 **다른 데이터에도 쓸 수 있게** 바꾸는 게 목표다.

지금 규칙들을 보면 두 종류가 섞여 있다.

- **데이터 사실** — 구매의 절반이 장바구니를 안 거친다, 단일 월이다. 이건 이 데이터에서만 참이다.
- **설계 판단** — 세션 속성과 상품 속성은 다른 분모를 쓴다, 결측률은 조건부로 재측정한다. 이건 어느 데이터에나 적용된다.

둘을 분리하면 후자는 그대로 두고 전자만 갈아끼우는 구조가 된다. 새 데이터셋에서는 프로파일링만 다시 돌리면 되도록.

## 실행

```bash
git clone https://github.com/FASTriver0714/dataagent.git
cd dataagent

python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

# MCP 등록 (절대경로여야 한다)
claude mcp add --scope project dataagent -- $(pwd)/.venv/bin/python $(pwd)/src/server.py
```

등록 후 Claude Code를 완전히 재시작해야 반영된다.

```bash
# 채점
python eval/score.py eval/responses.jsonl
```

데이터는 [eCommerce behavior data from multi category store](https://www.kaggle.com/datasets/mkechinov/ecommerce-behavior-data-from-multi-category-store) 2019년 10월분을 썼음. 용량이 커서 저장소에는 없음.
